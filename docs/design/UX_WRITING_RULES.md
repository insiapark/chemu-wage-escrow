# 체무 UX 라이팅 규칙

체무 두 앱(알바생 앱, 사장님 앱)의 화면 문구 규칙이다. 근거는 토스가 공개한 라이팅 원칙 원문이고, 2026년 11월 23일에 페이지를 직접 열어 확인했다. 규칙마다 출처 번호(S1~S18)가 붙어 있고, 자동 검사 규칙은 `ux_rules.json`, 검사 도구는 `uxlint.mjs`에 있다.

확인 표시
- [원문 확인] 페이지 본문에서 규칙 문장을 직접 읽었다.
- [원문 일부 확인] 규칙 문장은 본문에 있지만 예시가 이미지라 문구를 읽지 못했다.
- [원문 확인 못 함] 토스 공개 글에서 근거를 찾지 못했다. 체무 팀 기준으로만 쓴다.

원문 인용은 15단어 안으로 줄였고, 나머지는 자기 말로 요약했다. 나쁜 예와 좋은 예는 모두 체무 화면에 맞춰 새로 만든 문구다.

## 3. 규칙

규칙마다 "검사"에 적힌 아이디는 `ux_rules.json`의 자동 규칙이다. error는 고치고 내보내고, warn은 사람이 보고 고칠지 정한다.

### UX-01 해요체로 쓴다

- 원칙 요약: 제품 안의 모든 문구는 상황과 맥락에 상관없이 해요체로 통일한다. 회사 잘못으로 생긴 에러에도 해요체를 쓴다. 해요체가 토스 톤을 만드는 가장 큰 요소다.
- 출처: S7 해요체 [원문 확인], S3 [원문 확인], S4 [원문 확인]
- 체무 규칙: 제목, 본문, 버튼 밑 설명, 알림, 사장님에게 가는 문자 미리보기, 대화창까지 해요체로 쓴다. "~습니다", "~십시오", "~한다" 같은 해라체 평서문을 쓰지 않는다. "~할 수 있습니다"는 "~할 수 있어요"로 바꾸고, 빼도 뜻이 같으면 문장째 뺀다.
- 검사: 자동 UX-01a(격식 어미, error), UX-01b(~할 수 있습니다, error), UX-01c(해라체 끝, warn)

| 나쁜 예 | 좋은 예 |
|---|---|
| 오늘 일당이 보관되었습니다. | ₩92,880 보관했어요 |
| 출근 기록은 기록 탭에서 확인할 수 있습니다. | 출근 기록은 기록 탭에 있어요 |

### UX-02 능동형으로 쓴다

- 원칙 요약: 수동형보다 능동형 문장을 쓴다. "됐어요"는 "했어요"로 바꾼다. 수동형은 서비스 종료나 기간 만료, 연체·해지·적용처럼 사용자 행동의 결과를 알릴 때, 민감한 상황에서 안심시킬 때만 쓴다. "되어요"는 모두 "돼요"로 쓴다.
- 출처: S7 능동적 말하기와 예외 [원문 일부 확인]
- 체무 규칙: 돈을 움직인 사람(사장님, 체무, 나)을 주어로 세운다. "확정하면 보관돼요"처럼 사용자 행동의 결과를 미리 알리는 문장은 예외로 둔다. "되어지다", "처리되었", "완료되었"는 쓰지 않는다.
- 검사: 자동 UX-02a(이중 피동·처리 완료형, error), UX-02b("되어요", error), UX-02c("~됐어요", warn)

| 나쁜 예 | 좋은 예 |
|---|---|
| ₩5,160 더 보관됐어요 | 사장님이 ₩5,160을 더 보관했어요 |
| 11월 15일 근무 확정이 완료되었어요 | 사장님이 11월 15일 근무를 확정했어요 |

### UX-03 과한 높임을 뺀다

- 원칙 요약: "~시겠어요?", "~시나요?", "~께" 같은 과한 경어를 쓰지 않는다. 계시다는 있다, 여쭈다는 확인하다나 묻다, 께는 에게로 바꾼다. 빼서 어색하면 알고 싶은 정보를 주어로 세워 다시 쓴다. 사용자 맥락을 쓰는 질문, 상황을 추정하는 질문, 설문처럼 선의가 필요한 질문에만 "~시나요?", "~셨나요?"를 쓴다.
- 출처: S7 캐주얼한 경어 [원문 확인]
- 체무 규칙: 묻는 문장은 "~할까요?"로 쓴다. "사장님께"는 "사장님에게"로 쓴다. "~해 주시기 바랍니다" 대신 "~해 주세요"를 쓴다. "알려 드려요"는 원문 금지 목록에 없고 S8의 좋은 예에도 같은 꼴이 나와 그대로 쓴다. 공감 문장도 "고생 많았어요"처럼 높임 "시"를 뺀다.
- 검사: 자동 UX-03a(과한 높임, error), UX-03b("님께", warn), UX-03c("~시나요", warn)

| 나쁜 예 | 좋은 예 |
|---|---|
| 출근 처리를 진행하시겠어요? | 새싹편의점 연희점에 출근할까요? |
| 사장님께 알림 보내기 | 사장님에게 알림 보내기 |

### UX-04 긍정형으로 쓴다

- 원칙 요약: "안 돼요", "없어요"보다 "~하면 할 수 있어요"처럼 할 수 있는 일을 말한다. 일부 혜택만 못 받을 때도 긍정형으로 써야 서비스 전체를 못 쓴다고 오해하지 않는다. 부정형은 정책상 못 쓸 때(이유와 함께), 일부 기능만 막혔을 때(무엇이 막혔는지), 민감한 상황에서 안심시킬 때만 쓴다.
- 출처: S7 긍정적 말하기 [원문 일부 확인], S2 원칙 6 [원문 확인]
- 체무 규칙: 제목과 버튼은 할 수 있는 일로 쓴다. 본문의 "급여일 전에는 사장님도 꺼낼 수 없어요"는 알바생을 안심시키는 부정형이라 예외다. 한 문장에 부정을 두 번 쓰지 않는다.
- 검사: 자동 UX-04a(제목·버튼 부정형, warn), UX-04b(부정 두 번, warn). 본문 부정형이 예외에 드는지는 사람이 본다.

| 나쁜 예 | 좋은 예 |
|---|---|
| 가게 30m 밖이라 출근할 수 없어요 | 가게 30m 안으로 오면 출근할 수 있어요 |
| 켜 두지 않으면 일당이 안 들어온 날에도 알림이 오지 않아요 | 알림을 켜 두면 일당이 안 들어온 다음 날 바로 알려요 |

### UX-05 권하고 강요하지 않는다

- 원칙 요약: 사용자가 스스로 고를 수 있게 권하고, 강요하거나 불안을 키워 행동을 끌어내지 않는다. "~해야 해요" 대신 "~할 수 있어요"를 쓴다. 부정적이거나 애원·호소하는 감정 표현은 다크패턴으로 본다.
- 출처: S1 Suggest over force [원문 확인], S2 원칙 6 [원문 확인], S7 다크패턴 [원문 확인]
- 체무 규칙: 안 들어온 돈 안내도 날짜와 할 수 있는 일로 쓰고 "반드시", "즉시", "불이익", "손해" 같은 말을 쓰지 않는다. 사장님에게 보관함을 채우라고 할 때도 같다.
- 검사: 자동 UX-05a(겁주는 말, error), UX-05b("~해야 해요", warn). 호소·애원 톤은 사람이 본다.

| 나쁜 예 | 좋은 예 |
|---|---|
| 즉시 보관함을 채우지 않으면 불이익이 생길 수 있어요 | 12월 1일까지 채우면 B님 몫으로 바로 보관돼요 |
| 알림을 꼭 켜야 해요 | 알림을 켜면 일당이 안 들어온 다음 날 알려요 |

### UX-06 잡초를 뺀다

- 원칙 요약: 넣든 빼든 뜻이 같은 단어(잡초)를 뺀다. 글자 수를 줄이는 것보다 의미 없는 단어를 없애는 것이 목표다. 원문에 나온 잡초 예는 "앞으로"와 "혹시"다.
- 출처: S1 Weed cutting [원문 확인], S6 [원문 확인]. 팀 잡초 목록(해당, 관련, 진행, 정상적으로, 성공적으로, 일단, 각종, 또한, 및)은 [원문 확인 못 함]
- 체무 규칙: 문장마다 낱말 하나씩 빼고 읽어 봐서 뜻이 같으면 뺀다. "해당 근무"는 날짜로 바꾼다.
- 검사: 자동 UX-06a(원문 잡초, warn), UX-06b(팀 잡초, warn)

| 나쁜 예 | 좋은 예 |
|---|---|
| 혹시 퇴근 버튼을 못 누르셨나요? | 어제 퇴근 기록이 없어요 |
| 해당 근무의 확정이 정상적으로 진행됐어요 | 사장님이 11월 15일 근무를 확정했어요 |

### UX-07 빈 문장과 되풀이를 뺀다

- 원칙 요약: 한 화면에서 같은 말을 되풀이하거나 허전해 보여서 넣은 문장을 지운다. 문장 하나하나는 괜찮아도 화면 전체에서 같은 말이 반복되는 문제가 신규 입사자 화면에서 자주 나온다.
- 출처: S1 Remove empty sentences [원문 확인], S5 [원문 확인]
- 체무 규칙: 대화창과 바텀시트는 뒤 화면에 이미 있는 문장을 다시 쓰지 않는다. 본문은 제목을 되풀이하지 않고 제목에 없는 정보(이유, 다음에 일어날 일)만 쓴다.
- 검사: 자동 UX-07a(같은 문장 되풀이, warn), UX-07b(본문이 제목 되풀이, warn). 목록 행마다 붙는 상태 표시("가게 30m 안에서 기록됨")와 이름·금액 줄은 세지 않는다.

| 나쁜 예 | 좋은 예 |
|---|---|
| 대화창 본문 "급여일 전에는 사장님이 꺼낼 수 없어요" (뒤 화면에도 같은 문장) | 대화창 제목 "이 돈은 12월 10일에 A님에게 나가요" 한 줄과 [채워 둔 돈 꺼내기] |
| 제목 "확인할 근무가 없어요" / 본문 "지금은 확인할 근무가 없어요" | 제목 "확인할 근무가 없어요" / 본문 "사장님이 모든 근무를 확정했어요" |

### UX-08 핵심 메시지 하나만 남긴다

- 원칙 요약: 사용자가 이미 알거나 지금 필요 없는 내용은 빼고 꼭 볼 정보만 남긴다. 한 문장에는 한 메시지만 담아 짧은 호흡으로 읽히게 쓴다. 바텀시트 제목은 한 줄로 쓴다.
- 출처: S1 Focus on key message, Easy to speak [원문 확인], S6 바텀시트 제목 [원문 확인]. 글자 수 기준은 [원문 확인 못 함] 팀 기준
- 체무 규칙: 제목은 공백 포함 40자 이하, 본문 한 문장은 50자 이하, 바텀시트 제목은 한 줄(20자 이하로 잡는다)로 쓴다. 숫자가 주인공인 화면은 숫자를 제목에 올린다.
- 검사: 자동 UX-08a(제목 40자, error), UX-08b(문장 50자, warn), UX-08c(바텀시트 제목 20자, warn)

| 나쁜 예 | 좋은 예 |
|---|---|
| 제목 "사장님이 근무를 확정하면 그날 일당이 채워 둔 돈에서 바로 보관되고 급여일에 들어와요" | 제목 "확정하면 그날 일당이 보관돼요" / 설명 "12월 10일 급여일에 한 번에 들어와요" |
| 문자 "B님의 11월 18일 ~ 20일 일당 ₩126,000과 주휴수당 ₩42,000, 모두 ₩168,000을 아직 보관 못 했어요." | 문자 "B님 몫 ₩168,000을 아직 보관 못 했어요. 11월 18일 ~ 20일 일당과 주휴수당이에요." |

### UX-09 소리 내어 읽기 쉬운 말을 쓴다

- 원칙 요약: 일상에서 말하지 않는 단어와 업계 전문 용어를 줄인다. 한자어, 문어체, 지나치게 긴 호흡을 피한다. 나이·학력·업계와 상관없이 누구나 아는 말을 쓰고 은어와 유행어를 조심한다. 한자어 명사는 동사로 풀어 쓰고, 어려우면 "{명사}가 {명사}해서" 꼴로 쓴다.
- 출처: S1 Easy to speak, Universal words [원문 확인], S7 명사+명사 지양 [원문 일부 확인]
- 체무 규칙: 6절 금지어 표의 업무 한자어는 쓰지 않는다. 최저임금, 주휴수당, 노동청 진정처럼 바꿀 말이 없는 법정 이름은 그대로 쓰고 처음 나올 때 한 줄로 풀어 준다.
- 검사: 자동 UX-09a(업무 한자어, error), UX-09b(맥락 따라 바꿀 말, warn)

| 나쁜 예 | 좋은 예 |
|---|---|
| 금일 일당 미지급분이 발생했어요 | 오늘 일당이 아직 안 들어왔어요 |
| 10시간 − 휴게 1시간 = 9시간 | 10시간 − 쉬는 시간 1시간 = 9시간 |

### UX-10 시스템 말을 쓰지 않는다

- 원칙 요약: 개발자만 읽을 수 있는 코드나 IT 용어로 된 문구는 사용자에게 뜻이 없다. 시스템 입장에서 맞는 말이라도 사용자가 해결 방법을 모르면 알맞은 문구가 아니다. "알 수 없는" 같은 말은 이해하기 어렵다.
- 출처: S2 원칙 4 [원문 확인], S1 Universal words [원문 확인]
- 체무 규칙: 예금토큰과 블록체인 구조는 화면 말로 드러내지 않는다. 토큰, 지갑, 스테이블코인, 블록체인, 컨트랙트, 해시는 "보관된 돈", "받을 곳", "누구도 고칠 수 없는 기록"으로 바꾼다. 수령자 지갑은 이후 확장 범위라 받을 곳 고르기 화면에서도 꺼내지 않는다.
- 검사: 자동 UX-10a(시스템·블록체인 말, error), UX-10b(오류·실패, warn)

| 나쁜 예 | 좋은 예 |
|---|---|
| 트랜잭션 처리 중 오류가 발생했어요 (E401) | 인터넷이 끊겨서 확정을 보내지 못했어요 / [다시 확정하기] |
| 지갑이 없어도 원화 계좌로 받을 수 있어요 | 월급은 내 은행 계좌로 받아요 |

### UX-11 버튼만 보고 다음 일을 알 수 있게 쓴다

- 원칙 요약: 다음 화면에서 무슨 일이 일어날지 문장에 힌트를 준다. CTA만 보고 다음 행동을 예상할 수 있어야 하고 라벨이 모호하면 안 된다. 행동을 요청하는 버튼 하나는 "~하기"로 쓴다. 버튼 문구만 "확인"에서 "결과 보기"처럼 결과가 보이게 바꿔도 사용자가 덜 헤맨다.
- 출처: S1 Predictable hint [원문 확인], S7 CTA 규칙 [원문 확인], S6 버튼 룰 [원문 확인], S8 [원문 확인]
- 체무 규칙: 행동 버튼은 "목적어 + ~하기"로 쓴다. "예", "아니요" 단독 버튼은 쓰지 않는다. "확인" 단독 버튼도 쓰지 않고, 다음 화면으로 넘어가기만 하면 "다음", 정보만 보고 닫으면 "닫기"로 쓴다.
- 검사: 자동 UX-11a("예·아니요", error), UX-11b("확인·완료·저장" 단독, warn), UX-11c("~하기"로 안 끝나는 행동 버튼, warn)

| 나쁜 예 | 좋은 예 |
|---|---|
| 퇴근할까요? [아니요] [예] | 퇴근할까요? [닫기] [퇴근하기] |
| 계약 내용 [확인] | 계약 내용 [동의하고 시작하기] |

### UX-12 물러나는 버튼은 "닫기"로 쓴다

- 원칙 요약: 다이얼로그 왼쪽 버튼은 "닫기"로 통일한다. "취소"는 진행 중인 작업이 취소된다고 오해할 수 있다. 버튼이 둘일 때 물러나는 쪽은 "닫기"나 "다음에"를 쓴다.
- 출처: S7 [원문 확인], S6 [원문 확인]. S11 예시 코드의 "아니오/예", "취소/확인"은 동작을 보여 주는 자리 표시용 문자열이라 따르지 않는다.
- 체무 규칙: 대화창 왼쪽은 "닫기", 알림 켜기처럼 권하는 바텀시트의 물러나는 버튼은 "다음에"로 쓴다. 정말 무언가를 끄는 버튼은 "알림 끄기"처럼 무엇을 끄는지 쓴다.
- 검사: 자동 UX-12a("취소" 단독, error)

| 나쁜 예 | 좋은 예 |
|---|---|
| ₩87,720으로 확정할까요? [취소] [확인] | ₩87,720으로 확정할까요? [닫기] [₩87,720으로 확정하기] |
| 알림을 켤까요? [취소] [켜기] | 알림을 켤까요? [다음에] [알림 켜기] |

### UX-13 주 버튼은 하나, 같은 문구는 한 번

- 원칙 요약: 화면에서 설명한 가치를 CTA에 그대로 반복하지 않는다. CTA 위에 과장되거나 중복된 보조 설명을 두면 버튼의 역할이 흐려진다.
- 출처: S7 다크패턴 CTA 규칙 [원문 확인]. 한 층에 같은 버튼을 두 번 두지 않는 기준은 [원문 확인 못 함] 팀 기준
- 체무 규칙: 한 층(화면 본문, 바텀시트, 대화창) 안에 같은 문구의 버튼을 두 번 두지 않는다. 대화창의 확정 버튼이 뒤 화면 버튼과 같은 것은 괜찮다. 버튼 밑 설명줄은 버튼 문구를 되풀이하지 않는다.
- 검사: 자동 UX-13a(같은 층 버튼 문구 중복, warn). 덤프에 `[채운버튼]` 머리표가 있으면 채운 버튼끼리 겹칠 때 error로 올린다. 지금 덤프 도구는 채운 버튼을 따로 표시하지 않아 문구 중복만 잡는다.

| 나쁜 예 | 좋은 예 |
|---|---|
| 오늘 화면 위쪽과 근무 카드에 [퇴근하기] 두 개 | 근무 카드에만 [퇴근하기], 위쪽은 상태 "근무 중" |
| [사장님에게 알림 보내기] 밑에 "사장님에게 알림을 보내요" | [사장님에게 알림 보내기] 밑에 "보내기 전에 갈 문자를 먼저 보여 드려요" |

### UX-14 버튼은 15자 안으로 쓴다

- 원칙 요약: 토스 공개 글에 버튼 글자 수 기준은 없다. 간결한 글쓰기(Concise)와 Predictable hint를 버튼 길이로 옮긴 팀 기준이다.
- 출처: [원문 확인 못 함] 팀 기준. 바탕은 S1 Concise
- 체무 규칙: 버튼 이름은 공백 포함 15자 이하로 쓴다. 금액, 이름, 날짜는 버튼 위 문장으로 올린다. 목록 행 전체가 눌리는 경우(달력 칸 "1 보관됨", 계좌 행, 상담 전화 행)는 버튼 이름이 아니라 행이라 길이를 재지 않는다.
- 검사: 자동 UX-14a(warn). 행 판정은 `ux_rules.json`의 `rowLeadPatterns`, `rowPatterns`, `rowMinSpaces`가 정한다.

| 나쁜 예 | 좋은 예 |
|---|---|
| [2개 확정하고 ₩222,912 보관하기] | 버튼 위 "어제 근무 2개, ₩222,912" / [2개 확정하기] |
| [사장님께 확정 요청 다시 보내기] | [확정 요청 다시 보내기] |

### UX-15 에러는 이유와 해결 방법, 해결 버튼까지 쓴다

- 원칙 요약: 최고의 에러는 생기지 않는 에러라서 문구보다 흐름을 먼저 고친다. 실패했다는 사실만 말하지 말고 스스로 해결할 방법을 알려 준다(가장 중요한 원칙). 해결까지 드는 수고를 탭 한 번으로 줄인다. 에러 메시지의 기조는 사용자를 다음 화면으로 안내하는 것이고, 비슷한 에러는 같은 문구로 통일한다.
- 출처: S2 원칙 1·3·5 [원문 확인], S3 [원문 확인]
- 체무 규칙: 제목은 일어난 일을 사용자 말로, 설명은 이유와 할 일로, 버튼은 해결 행동으로 쓴다. 같은 종류의 에러는 템플릿 하나를 쓴다. 예: 제목 "{무엇}을 불러오지 못했어요" / 설명 "인터넷 연결을 확인하고 다시 불러와 주세요" / [다시 불러오기].
- 검사: 자동 UX-15a(문제를 알리는 제목인데 해결 버튼 없음, warn). 이유 문장과 템플릿 일치는 사람이 본다.

| 나쁜 예 | 좋은 예 |
|---|---|
| 입금에 실패했어요 [확인] | 12월 10일 자동 입금이 안 됐어요 / 받을 곳 정보가 은행 정보와 달라서 보내지 못했어요 / [받을 곳 고치기] |

## 7. 자동 검사 도구

### 실행

```
node uxlint.mjs <text.json> <ux_rules.json> <결과.md>
```

- 도구 위치: `uxlint.mjs` (같은 폴더의 `textdump.mjs`가 덤프를 만든다)
- 입력: `[{i, label, text}]`. text의 줄 앞 머리표 `[제목] `, `[버튼] `, `[시트] `, `[대화창] `을 읽는다. 채운 버튼을 구분하려면 `[채운버튼] ` 머리표를 쓴다.
- 결과: 화면별 위반(규칙, 등급, 문장, 고칠 방향)과 끝의 규칙별 개수 표
- 종료 코드: error가 하나라도 있으면 1, 없으면 0, 인자나 파일 문제는 2

### 오탐을 막는 장치

| 장치 | 하는 일 | 설정 |
|---|---|---|
| 데이터 가리기 | 금액(₩92,880, 10,320원), 시각(오후 10:00), 날짜(11월 15일), 계좌·전화번호(***-21-3021), 숫자를 `#`으로 바꾼 뒤 검사한다. 한글이 두 글자도 안 남는 줄은 데이터 줄로 보고 되풀이·문장 길이 검사에서 뺀다 | 도구 안 `MASKS` |
| 수식 기호 | 빼기 기호 "−"(U+2212)는 대시 검사에서 뺀다 | UX-19b 정규식 |
| 버튼 판정 | 숫자 배지("1"), 탭(출퇴근, 오늘), 필터 칩(전체, 이번 달), 상태 버튼("사장님 답을 기다리고 있어요"), 목록 행을 행동 버튼과 가른다. 길이·문법 검사는 행동 버튼 이름에만 한다 | `navButtons`, `chipButtons`, `closeButtons`, `chipMaxLength` |
| 목록 행 | "1 보관됨", "A A님 몫 …"처럼 숫자나 이니셜로 시작하는 행, 계좌(***)·시각·세 자리 이상 숫자가 든 행, 띄어쓰기 4번 이상인데 "~기"로 끝나지 않는 행은 버튼 이름이 아니라 행으로 본다 | `rowLeadPatterns`, `rowPatterns`, `rowMinSpaces` |
| 버튼 밑 설명 | "출근하기 출근하면 오늘 일당 보관이 시작돼요"처럼 이름 뒤에 설명이 붙은 버튼은 첫 "~기"까지를 이름, 나머지를 본문으로 검사한다 | 도구 안 `analyzeButton` |
| 낱말 경계 | "입금일" 안의 "금일"처럼 낱말 중간에 걸리는 짧은 한자어는 앞 글자가 한글이면 넘긴다 | 용어의 `"start": true` |
| 예외 구간 | 규칙이나 용어마다 예외 구간을 지운 뒤 검사한다(예: "최저임금" 안의 "임금", "모바일 데이터" 안의 "데이터", "안 됐어요"의 "됐어요") | 규칙·용어의 `except` |
| 줄 무시 | 시연용 안내 줄("프로토타입 · …")은 검사하지 않는다 | `ignoreLines` |
| 부정 세기 | 용어집의 고정 표현(안 들어온 돈, 보관 못 한 돈, 못 쉰)은 부정 두 번 검사에서 세지 않는다 | `negationIgnore` |
| 되풀이 | 문장으로 끝나는 것(~요, ~다, 마침표, 물음표)만 세고, 같은 층 안에서는 한글 12자 이상, 화면과 시트·대화창 사이에서는 8자 이상일 때 잡는다 | `repeatMinLength`, `repeatMinLengthSameBlock` |
| 버튼 중복 | 같은 층(화면 본문, 시트, 대화창) 안에서만 센다 | 도구 안 `duplicateButton` |

## 8. 화면 읽기 이름 (v35부터)

보이는 글은 그대로 두고, 기호가 든 글과 여러 칸으로 된 행에만 화면 읽기가 읽을 말을 따로 둔다. 보이는 쪽은 `aria-hidden="true"`, 읽는 쪽은 화면에 보이지 않는 글이다. 화면 읽기는 이름 뒤에 "버튼", "탭, 4개 중 1번째", "스위치, 켜짐"을 스스로 붙이므로 이름에 역할을 넣지 않는다("오늘 탭이에요"가 아니라 "오늘").

| 대상 | 보이는 글 | 읽는 말 |
|---|---|---|
| 금액 | 92,880원 | 그대로 |
| 시각 | 오후 10:00, 오전 7:30 | 오후 10시, 오전 7시 30분 |
| 범위 | 오후 10:00 ~ 오전 8:00, 11월 9일 ~ 15일, 월 ~ 금 | 오후 10시부터 오전 8시까지, 11월 9일부터 15일까지, 월요일부터 금요일까지 |
| 요일 묶음 | 토, 일 | 토요일, 일요일 |
| 계산식 | ×, ÷, +, −, = | 곱하기, 나누기, 더하기, 빼기. "="는 결과로 끝나면 받침에 따라 "은"이나 "는", 계산이 이어지면 "하면" |
| 가운뎃점 | · | 쉼표로 쉬어 읽는다 |
| 거리 | 30m | 30미터 |
| 가린 계좌 | 국민은행 ***-21-3021 | 국민은행 계좌, 끝자리 3021 |
| 가린 전화번호 | 010-****-5678 | 끝자리 5678인 번호 |
| 기록 번호 | 0x4be1…92af | 기록 번호, 끝자리 92af |
| 상담 전화 | 1350 | 1 3 5 0(한 자리씩) |
| 흐르는 시간 | 2:14:08, 2:48 | 근무한 시간 2시간 14분 8초, 남은 시간 2분 48초. 값이 바뀌면 읽기 이름도 함께 바뀌고, 저절로 읽어 주지는 않는다 |
| 배지 | 보관됨, 확정 대기 | 그대로. 어미를 붙이지 않는다 |
| 배지 숫자 | 확인 필요 1 | 확인 필요 1개 |
| 알림 종 | 숫자 1 | 알림, 읽지 않은 알림 1개 |
| 읽지 않은 점 | 점 | 행 이름 끝에 "읽지 않음" |
| 누르는 행 | 제목, 설명, 배지, 오른쪽 금액 | 쉼표로 이은 이름 하나: "11월 15일 일요일, 오후 10시부터 오전 8시까지, 9시간, 보관됨, 92,880원" |
| 비교 카드 | 두 칸 | 한 문장: "A님 기록 오전 8시, 사장님이 고친 시간 오전 7시 30분" |
| 진행 단계 | 원 색과 아이콘 | 단계 앞에 상태: 끝남, 지금, 확인 필요, 문제 있음, 다음 |
| 스위치 행 | 제목과 설명 | "제목, 설명". 켜짐과 꺼짐은 스위치 상태로 읽힌다 |
| 그림 | 히어로, 작은 사물, 행 아이콘, 네 칸 | 읽지 않는다(빈 alt, aria-hidden) |
| 버튼, 탭 | 행동 이름 | 보이는 글 그대로. 기호가 있으면 위 표대로("오전 7시 30분으로 고치기") |

같은 말을 두 번 읽지 않는다. 배지와 행 제목이 같은 말이면 한 번만, 아이콘과 글자가 같이 있으면 글자만, 비교 카드 안의 칸은 숨긴다. 사용자가 써 넣은 글(고치는 이유 같은 입력값)은 바꾸지 않는다.

검사: 읽는 차례대로 이름을 뽑은 읽기 덤프에서 기호나 콜론 시각이 남은 줄을 센다. 입력값을 뺀 0줄이 목표다. 읽기 덤프를 uxlint에 넣으면 쉼표로 이은 행 이름 때문에 UX-08b(50자), 종 버튼 이름 때문에 UX-11c가 warn으로 나온다. 문장이 아니라 목록이라 고치지 않고, error만 0이면 된다.
